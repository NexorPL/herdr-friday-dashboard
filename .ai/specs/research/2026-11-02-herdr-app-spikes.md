# herdr-app spikes (Phase 1, step 2)

Run on 2026-11-02 against herdr-app 0.1.12 (`herdr-app --version`; the spec was written against 0.1.11 and the type files read the same). A scratch mod `friday-spike` ran in a temporary tab with two panes of the same mod (`tab.new --mod friday-spike --props '{"id":"a"}'`, then `pane.split` with `"id":"b"`). Each copy wrote its findings to a hidden file in its own folder. Local helper servers on 127.0.0.1 served the fetch cases. The scratch mod, the tab and the servers were removed afterwards.

Plain Node scripts could not answer these questions, because the mod runtime is QuickJS inside herdr-app. `herdr-app check` passed for the scratch mod. One thing `check` showed: `props()` is `null` while a mod is checked, so mod code must write `(props() || {})`.

## Answers

| # | Question | Answer | Evidence |
|---|---|---|---|
| 1 | Do copies share module scope? | **No.** Each copy has its own module instance. | Two panes of one mod, started within 7 ms of each other, printed different `Math.random()` tokens from a module-level constant, and each counted `copies = 1` on a module-level counter. |
| 2 | How to time out `fetch`? | `AbortController`, `AbortSignal` and `AbortSignal.timeout` do **not exist**. Race the `fetch` promise against `cx.timer.after(ms, ...)` rejecting a promise. The fetch itself is abandoned, not cancelled. | `typeof AbortController === "undefined"`. A `Promise.race` against a 2000 ms timer rejected after 2045 ms and 2049 ms against a server that never answered. |
| 3 | Is `writeTextFile` outside the app home refused? | **No, it is allowed** (checked at a path in the user's temp folder), with the same compare-and-swap rules as inside. `fs/promises` writes, however, are refused outside granted roots (`capabilities.fs.write`); `fs.writeFile` inside the app home works. `readTextFile` reads outside the app home. `fs.readFile` outside the home is refused. | Create with `expected = null` resolved; create over an existing file rejected; overwrite with the matching snapshot resolved; overwrite with a stale snapshot rejected with "The file changed outside Herdr. Reload before saving" and left the file unchanged. All four outcomes held both inside and outside the app home. Consequence: the ledger (any path) is read with `readTextFile`; transcripts outside the home (Phase 6) cannot use `fs.readFile`, which contradicts the spec's "Transcripts are read with `fs.readFile`, which has no such limit". Phase 6 must re-check this. |
| 4 | How large can `shared()` get? | 4 MiB in one key worked: `setShared` took 16 ms and `shared()` returned the whole value at once, in both copies. Larger sizes were not tried, because every value is persisted in the owner's `shared.json`. | 64 KiB, 512 KiB, 1 MiB and 4 MiB strings: set in 0, 2, 5 and 16 ms. Design rule for Friday: keep each `friday.*` value well under 1 MiB. |
| 5 | Does `Date` give local offsets? | **Only the offset in force now, applied to every date.** `getTimezoneOffset()` gave -60 (CET) for January and for July, so a July local time is converted with the winter offset and is an hour off. Parsing a date string with an explicit offset (`...+02:00`) or `Z` is correct. `toLocaleTimeString()` exists but formats in en-US, so Friday formats times itself. | `new Date(2026, 6, 15).getTimezoneOffset() === -60` on a machine in a Central European time zone, where July is -120. `local_from_parts` for 2026-07-01 12:00 gave 11:00Z. Consequence: Friday's own "today" and clock use the current offset only (correct for the clock); anything that needs another date's local time (meetings in Phase 3) must come from the feed's `VTIMEZONE`, not from `Date`. |
| 6 | Does `ical.js` load? | **Yes.** `ical.js` 2.2.1 (the ESM build from the npm package, 261 KB) loaded with a dynamic `import("./ical.js")` and expanded a daily `RRULE:COUNT=6` with a `VTIMEZONE` (a Central European zone), one `EXDATE`, across a DST change, to the correct five UTC times. Phase 3 can vendor it. | Occurrences: 2026-10-26, 27, 29, 30, 31 at 08:30Z. |

## Other findings that change the code

- **The hub uses leases.** From answer 1: no module singleton is possible, so step 7 builds `core/lease.js` and the leases in `shared()`. `setShared` is last-writer-wins and visible to the other copy at once. In a race where both copies wrote their own lease at the same moment, both then read the same winner after 600 ms. A "read, take it only if free, then read again to confirm" sequence also ended with both copies agreeing on one holder. So Friday takes a lease, waits a moment and reads it back before fetching.
- **`fetch` responses have no headers.** The response object has only `status`, `ok`, `url`, `text` and `json`; `response.headers` is `undefined`. `Retry-After` cannot be read, so the backoff always uses its own doubling. `core/backoff.js` keeps the `retryAfter` argument (and the header parser) so that it works the day herdr-app exposes headers. A 429, 401, 404 and 5xx all resolved with their status (a non-2xx status does not reject). A refused connection rejects.
- **`fetch` rejections carry the URL.** The rejection message reads "fetching <full url> failed: ...". Because the iCal address is a secret, Friday never shows or logs a rejection's message, only the source name.
- **`Buffer` base64 is broken.** `Buffer.from("user:pass").toString("base64")` returned an empty string (and `toString("hex")` too), although `.length` was right. `btoa` and `atob` exist and work (`btoa("user:pass")` gave `dXNlcjpwYXNz`). Basic auth in Phase 2 and 4 therefore uses `btoa` (with UTF-8 handled first), not `Buffer` as the spec says.
- **Missing globals:** `AbortController`, `AbortSignal`, `TextEncoder`, `structuredClone`, `Intl`. Present: `URL`, `URLSearchParams`, `queueMicrotask`, `performance`, `crypto`, `btoa`, `atob`. `setTimeout` and `setInterval` exist as functions but the herdr-app rules forbid them; Friday uses `cx.timer`.
- **A long job is ended without a trace** (measured 2026-11-02 while debugging Settings > Calendar). herdr-app ends a script job that runs about 0.5 s without giving control back: a 450 ms busy loop in `cx.spawn` finished, 600 ms and 1200 ms ones stopped, and neither their `catch` nor their `finally` ran; `herdr-app status` showed no error, and the copy's timers kept running. Six 200 ms slices separated by `await Promise.resolve()` were also stopped; separated by `await cx.sleep(0)` they finished. So slow work yields with `cx.sleep(0)` (the iCal parse does, `core/meetings.js`), and state set before an `await` that a `finally` would undo needs a timeout of its own (the hub's `STUCK_MS`, the Test button's give-up).
- **`readTextFile` stops at 1 MiB** with the error "Text file exceeds 1 MiB" (a 1 MiB + 10 byte file), so the ledger's "file too large" state is that error.
- **Concurrent copies and one file.** In two earlier runs, where two copies ran the same write sequence at the same moment (on the same path, then on paths of their own while an older build was still reloading), calls were rejected with the stale-snapshot error even though the files did change. Run by one copy alone, the semantics were exact (answer 3). Treat every `writeTextFile` rejection as "re-read and retry once", as the spec already says, and do not trust a single rejected call to mean the file is unchanged.
- **Side effect on the owner's `shared.json`.** The `shared()` size test left the keys `friday-spike.big` (empty string), `friday-spike.x`, `friday-spike.lease` and `friday-spike.lease2` (null) in the app's `shared.json`. They are empty and harmless, and Friday does not read them.
